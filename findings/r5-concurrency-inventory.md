### 3.1 Lead notes on the strongest rows

- **Open defect, A1-1 + A1-20 (new, testable).** Both path-keyed caches return the *pass-1 instance* of op1's manifest P (seq N) to op2 in pass 2. With only `filteredManifests` cleared, `manifestsWithMetadata.get(P@N+1)` hits the equal-by-path key and returns P@N. With only `manifestsWithMetadata` cleared, `filterManifest` returns the cached P@N and the loader returns it verbatim (`snapshotId != null`). So each cache masks the other, and r2 §6 only ever cleared them **one at a time**; the one row that cleared both (`all`) also cleared `new`, which removes the symptom by path churn and confounds it. Prediction: `-Ddst.invalidateFilterCache=filter,withmeta` → flip 0/200 with manifest-write count unchanged at 1200 (no path churn). If it stays 200/200, A1's mechanism is refuted. `FilterCacheProbe` now accepts comma-separated groups and throws on an unknown name (dst/ change). **RESULT: CONFIRMED** — joint eviction 0/200 with manifest writes 1200; control, `filter` alone and `withmeta` alone each 200/200. See findings/r5-open-defect-cause.md.
- **A2-9, IncrementalFileCleanup swallows read failures of retained manifest lists** — data-loss shaped, on the default expiry path for main-only tables, after a transient fault. DST cannot currently see it because `FakeFileIO` injects no read faults: an invariant/fault set that predates the hazard. Decider: DST with a read fault; calibrate the fault by showing `ReachableFileCleanup` throws instead of deleting.
- **A2-1, RemoveSnapshots.idsToRemove accumulates across retries.** Lead reading of the consequence: a retention-policy violation (a snapshot the pass-2 policy retains is expired), or a spurious non-retryable `IllegalArgumentException` if it became a ref head; files still reachable are protected by the cleanup's own reachability walk. DST I5 is reachability-based and cannot fire on this — needs a retention invariant.
- **D-31, SparkTableUtil.importSparkPartitions deletes manifests on any Throwable, including CommitStateUnknownException.** On v2+ with snapshot-id inheritance those manifests are committed as-is, so a commit that landed with a lost acknowledgement leaves the live snapshot pointing at deleted manifests. Same shape #10373 fixed in core. Decider: engine DST (or a core-level harness calling `SparkTableUtil` with a land-then-lose-ack catalog).
- **B-122, VariantWriter.INSTANCE shares a mutable buffer JVM-wide.** Two threads writing Avro variant columns can interleave `serialize` and `encoder.writeBytes`. Decider: jcstress — the textbook instruction-level target.
- **C-3/C-8, C-11/C-13: lease-only lock protocols with no fencing** (Hive with lock on passes no expected location; Glue skips the VersionId CAS when a DynamoDB lock manager is set). Classic lease-expiry lost update. Decider: TLA+ target 3 with an explicit clock. Agent C's state machines (§6.2) are the starting spec.

### 6.2 Lock state machines for TLA+ (slice C)

**MetastoreLock (one instance per doCommit attempt):**
- **Process-local states:** `Init → JvmLocked → Creating → Waiting → Acquired(heartbeating) → Released`.
- **Init → JvmLocked:** `commitLockCache.get(fullName).lock()` (444-445). This is a fair ReentrantLock and blocks with no timeout.
- **JvmLocked → Creating:** `client.lock(EXCLUSIVE, TABLE, agentInfo)` with retries (292-348). The response gives `{lockId, state ∈ {ACQUIRED, WAITING, NOT_ACQUIRED, ABORT}}`. On TException, `showLocks` matched by agentInfo is used.
- **Waiting:** poll `checkLock(lockId)` with backoff of 50 ms × 1.5 up to 5 s, for at most `lockAcquireTimeout` = 180 s (204-229). Leaving the loop in any state other than ACQUIRED calls `unlock(lockId)` (237-239) and throws LockException.
- **Acquired:**
  - `hmsLockId := lockId`.
  - Schedule heartbeat: first beat at `interval/2` = 120 s, then every 240 s, at fixed rate (496-499).
  - A heartbeat failure on TException/InterruptedException sets `encounteredException` and stops the task permanently. On RuntimeException it stops the task silently (C-4). There is no retry.
- **Commit critical section** (HiveTableOperations 258-336): `read(loc)`, `check loc == base`, `ensureActive`, `write(loc')` with no CAS, `ensureActive`. A LockException from the second `ensureActive` maps to CommitStateUnknown.
- **Released:** `heartbeat.cancel(false)`, executor shutdown, `unlock(hmsLockId)` (failures only logged, 386-428), release the JVM lock (448-453). This always runs from doCommit's finally (HiveOperationsBase:195-205).
- **Server side** (not in repo): the HMS lock is EXCLUSIVE per table. It expires when `now - lastHeartbeat > hive.txn.timeout` (default 300 s). Heartbeats also arrive implicitly from lock/checkLock calls.
- **Safety to check:** at most one writer whose `write` lands while it holds the lease. This is violated because `ensureActive` is a point check and `write` carries no fencing token.

**DynamoDbLockManager (per catalog, shared):**
- **Row:** `{entityId, ownerId, version(uuid), leaseDurationMs}`.
- **acquire:** loop until 180 s pass (5 s fixed interval):
  - `getItem` (consistent read).
  - If the row is absent: `putItem` if not exists.
  - Otherwise: sleep `leaseDurationMs` (15 s), then `putItem` if `version == observed`.
  - On success, start a heartbeat at fixed rate, initial delay 0, every 3 s: `putItem` with a new version, conditional on `ownerId == me`. Failures are logged and the next beat is tried.
- **release:** `deleteItem` conditional on `ownerId == me` (up to 5 attempts on throttling), then cancel the heartbeat if the owner matches.
- **Implicit lease:** a waiter takes over if the row's version did not change during its own sleep of `leaseDurationMs`. No clocks are compared.
- **Holder:** never re-validates ownership before writing to Glue.

### 6.5 Notable, slice A2

1. **A2-1 (high): RemoveSnapshots.idsToRemove keeps pass-1 ids into pass 2.**
   - `internalApply()` adds every non-retained id to the field `idsToRemove` (core/RemoveSnapshots.java:233-236). Nothing ever clears it. The commit retry (:361-373) and BaseTransaction's re-apply both call `internalApply()` again.

     1. Pass 1, on base0: snapshot S, an old ancestor of main snapshot S', is not retained, so it goes into `idsToRemove`.
     2. A concurrent commit creates branch B at S', with `minSnapshotsToKeep` (or `maxSnapshotAgeMs`) set so that S is retained.

(b) The only Iceberg-commit-retry-surviving state here is the kafka-connect `SnapshotAncestryValidator` (C-24), which re-reads ancestry on every attempt.

### 6.8 Notable, slice D

- **D-31 (high): `SparkTableUtil.importSparkPartitions`, spark/v4.1/.../SparkTableUtil.java:651-664. Same in v4.2:651-664 and v3.5:906-919.**
  - What the code does: `catch (Throwable e) { deleteManifests(targetTable.io(), manifests); throw e; }`. There is no CommitStateUnknownException carve-out.
  - Retry sequence:
    1. `add_files` runs on a v2 table. Snapshot-id inheritance is on (the default for format ≥ 2), so `appendManifest` puts the staged manifests into `appendManifests` and writes them into the manifest list unchanged (MergingSnapshotProducer.java:326-332, 1138-1140). Merging only happens past the min-count-to-merge.
    2. The catalog commit succeeds, but the response is lost. SnapshotProducer throws CommitStateUnknownException and, by design, does not clean `appendManifests` (1126-1131).
    3. SparkTableUtil deletes those same manifest files. The table's current snapshot now references deleted manifests, so the imported data is unreadable.
  - Contrast RewriteManifestsSparkAction.java:410-417 (D-29), which guards this correctly.
- **D-2 (high): streaming idempotency ignores branch and WAP.** SparkWrite.java:582-617; v4.2 has the same code at 601/618-619.
  - Retry sequence:
    1. A `writeStream` targets branch `b` (via `toBranch`, 264) or uses WAP (`stageOnly`, 260).
    2. Epoch N commits to `b`. The driver dies before Spark writes `commits/N`.
    3. On restart Spark replays epoch N with the same query id. `commit(N)` refreshes, then `findLastCommittedEpochId()` starts from `table.currentSnapshot()` (605), i.e. main. The snapshot on `b` is not an ancestor of main, so the walk returns null.
    4. `doCommit` appends the replayed files again, so branch `b` contains epoch N's rows twice.
  - SparkWriteBuilder.toStreaming (161-171) does not reject branch or WAP targets.
- **D-10 (med): lost update on `BaseCommitService.succeededCommits`.** core/.../BaseCommitService.java:62, 230.
  - Why it races: `offer()` (145-151) calls `commitReadyCommitGroups()` on the caller's thread, which is a Rewrite-Service pool thread (RewriteDataFilesSparkAction.java:357). Several pool threads can therefore commit and then do `succeededCommits++` at the same time.
  - Interleaving:
    1. Threads T1 and T2 both read 3.
    2. Both write 4. One success is lost.
    3. `failedCommits = totalCommits - succeededCommits()` (RewriteDataFilesSparkAction.java:361) is one too high.
    4. With `max-failed-commits` at the boundary, the action throws RuntimeException (371-381) even though every commit landed.
  - It reports the wrong result; no data is lost.
- **D-36 (med): equality-delete executor cache keyed by location only.** SparkExecutorCache.java:107-116 with data/.../BaseDeleteLoader.java:109-112.
  - Key vs. value: the key is `table.name() + "_" + deleteFile.location()`, but the value is `readEqDeletes(deleteFile, projection)`.
  - Sequence:
    1. Query A (current schema, `id` promoted int→long) and query B (time travel to a snapshot whose schema has `id: int`) run at the same time on one executor.
    2. A caches D's rows with Long values.
    3. B gets A's cached rows and puts them into `StructLikeSet.create(B's int projection)`.
    4. B's Integer data rows do not match the Long delete keys, so B returns rows that should be deleted.
  - Invalidation happens only per table-name group when a broadcast table is closed (SerializableTableWithSize.java:93-99), so entries are shared while both queries are alive.
- Brief context (sequence number surviving into a pass-2 manifest list): no Spark v4.1 path re-applies a multi-op BaseTransaction. Staged tables (StagedSparkTable.commitStagedChanges, :33-35) commit one append per create/replace transaction. The only deliberate value carried across retries in this slice is D-9, the `dataSequenceNumber` pinned from `startingSnapshotId`, which is intended behaviour.

### 6.9 Notable, slice E

- **E-33 (high)** `BaseCoordinator.java:86-90` + `94-109`. Sequence: table B's LockRemoverOperator sends a release (it sends one on every watermark, LockRemoverOperator:116-123) before B's TriggerManager registers, so it lands in PENDING (103). Table A's TriggerManagerCoordinator then runs `registerLock`, which calls `PENDING.forEach(handleReleaseLock)`. The B event still has no consumer and is added back to the same ArrayList (103) inside the forEach, so ArrayList.forEach throws ConcurrentModificationException. That is caught at 206-209 and calls `context.failJob`. Separately, when the Iceberg classes are shared across jobs (session cluster, runtime jar in lib/): job X `close()` (122-125) or `resetToCheckpoint()` (142-145) clears every lockId's consumer. Job Y's TriggerManagerOperator never re-registers (it registers only in initializeState, TriggerManagerOperator:174), so `lockTime` is never cleared and Y's maintenance stops permanently while PENDING grows. The coordination lock is the default (TableMaintenance.java:285). v1.20: identical.
- **E-34 (med)** `BaseCoordinator.java:83, 242-247`. The consumer closure registered by the TriggerManagerCoordinator is invoked on the LockRemoverCoordinator's executor thread. It reads the other coordinator's plain HashMap `gateways`, which is mutated on its own thread at 187/157/174. There is no happens-before. If that coordinator is between `subtaskReset` and `executionAttemptReady`, `checkState(!gateways.isEmpty())` throws on the LockRemover thread, and the job fails. v1.20: identical.
- **E-45 (med)** `EqualityConvertCommitter.java:226-234`. `catch (Exception e) { deleteUncommittedDVs(); }` covers every non-CSUE exception. Core only cleans on CleanableFailure under strict cleanup (`SnapshotProducer.java:541`, `TableOperations.java:127` default true; the #10373 policy). Sequence: the RowDelta commit reaches the catalog and lands, then the client gets a non-CSUE, non-cleanable RuntimeException (for example a transport error in a catalog that does not translate it to CSUE). The committer deletes the DV puffins that the new snapshot references, so reads fail on missing DVs, or deleted rows reappear if the DV is skipped. v1.20: identical.
- **E-4 (med)** `SinkUtil.java:90-104`. The walk follows `parentId` from the branch head and stops at the first missing parent. Sequence: ckpt N commits (summary max-ckpt=N), and the job fails before ckpt N+1. During the outage other writers commit to the branch and an expire (retainLast k, older-than) removes this job's snapshot. On restore the walk returns -1, so `tailMap(-1)` (IcebergFilesCommitter:196) or `tailMap(-1)` (IcebergCommitter:164) includes ckpt N again. Outcomes: NotFound on the deleted temp manifest, which crash-loops the job; or duplicate data if the manifest survived. Manifests survive when the swallowed delete in E-9 failed, or always under `tableMaintenanceEnabled` (IcebergCommitter:210). DynamicCommitter also re-commits here (same walk at 190-209). Its in-retry validator does not help, because the validator uses the same ancestry. v1.20: same.
- In-retry duplicate guard asymmetry (E-6 vs E-14): only DynamicCommitter installs `validateWith(MaxCommittedCheckpointIdValidator)`, which runs on every core retry attempt. IcebergFilesCommitter (373-396) and IcebergCommitter (312-328) rely on the catalog never reporting CommitFailed for a commit that landed. I marked this low because it requires the catalog to break that contract.
- Re the open BaseTransaction defect: no Flink v2.3 commit path in this slice uses BaseTransaction. Every commit is a fresh single SnapshotUpdate (`table.newAppend/newRowDelta/newReplacePartitions/newRewrite`). `newTransaction` appears only in `util/FlinkAlterTableUtil.java:45,76` (schema/property DDL). Nothing here carries a pass-1 sequence number into a later manifest list.
